  4.3 The Review Loop (Self-Healing)

  This is the critical piece that eliminates your involvement:

  PHASE 4 (Implement) → PHASE 5 (Test) → PHASE 6 (Review)
                             │                    │
                      Tests fail?            Blockers found?
                             │                    │
                             ▼                    ▼
                      ┌─────────────────────────────────┐
                      │       FIX AGENT (new context)    │
                      │                                   │
                      │  Receives ONLY:                   │
                      │  - Original spec                  │
                      │  - Current diff                   │
                      │  - Failure/blocker description     │
                      │  - Conventions + memory           │
                      │                                   │
                      │  Does NOT receive:                │
                      │  - Previous implementation context │
                      │  - Previous agent's reasoning      │
                      │                                   │
                      │  (Fresh eyes = better fixes)       │
                      └─────────────────────────────────┘
                                      │
                                      ▼
                              Back to PHASE 5

                      Loop counter: max 5 iterations
                      If exceeded: PR created anyway with
                      ⚠️ UNRESOLVED BLOCKERS section

  Why fresh context for the fix agent? An agent that wrote buggy code is biased
  toward defending its approach. A fresh agent sees only the diff and the
  problem — it's more likely to find the right fix.

  7. Orchestrator Implementation Sketch

  // orchestrator.ts (pseudocode)

  interface Task {
    id: string;
    description: string;
    type: 'feature' | 'bug-fix' | 'enhancement';
    clarificationAnswers: Record<string, string>;
  }

  async function runTask(task: Task): Promise<string> {
    const worktree = await createWorktree(task.id);
    const state = loadOrCreateState(task.id);

    // PHASE 1: Classify (already done — task.type)

    // PHASE 2: Clarity (if needed — for features/enhancements)
    if (!state.phases.clarity.completed) {
      const clarityOutput = await runClaudeAgent({
        worktree,
        prompt: buildPrompt('feature-clarity', task),
        tools: ['Read', 'Glob', 'Grep'],  // read-only
      });
      savePhaseOutput(state, 'clarity', clarityOutput);
    }

    // PHASE 3: Plan (features only)
    if (task.type === 'feature' && !state.phases.plan.completed) {
      const planOutput = await runClaudeAgent({
        worktree,
        prompt: buildPrompt('feature-plan', task, state.phases.clarity.output),
        tools: ['Read', 'Glob', 'Grep'],  // read-only
      });
      savePhaseOutput(state, 'plan', planOutput);
    }

    // PHASE 4-6: Implement → Test → Review (with loop)
    let loopCount = 0;
    while (loopCount < MAX_LOOPS) {
      // Implement
      await runClaudeAgent({
        worktree,
        prompt: buildPrompt('implement', task, state),
        tools: ['Read', 'Write', 'Edit', 'Glob', 'Grep', 'Bash'],
      });
      await gitCommit(worktree, `feat: implement ${task.id}`);

      // Test
      const testResult = await runTests(worktree);
      if (!testResult.passed) {
        loopCount++;
        await runClaudeAgent({  // Fix agent (FRESH context)
          worktree,
          prompt: buildFixPrompt(task, testResult.output),
          tools: ['Read', 'Write', 'Edit', 'Glob', 'Grep', 'Bash'],
        });
        continue;
      }

      // Review (FRESH context — diff only)
      const diff = await gitDiff(worktree);
      const review = await runClaudeAgent({
        worktree,
        prompt: buildPrompt('pr-review', task, diff),
        tools: ['Read', 'Glob', 'Grep'],  // read-only
      });

      const blockers = parseBlockers(review);
      if (blockers.length === 0) break;

      loopCount++;
      // Fix blockers (FRESH context)
      await runClaudeAgent({
        worktree,
        prompt: buildBlockerFixPrompt(task, diff, blockers),
        tools: ['Read', 'Write', 'Edit', 'Glob', 'Grep', 'Bash'],
      });
    }

    // PHASE 7: PR Description
    const prBody = await runClaudeAgent({
      worktree,
      prompt: buildPrompt('pr-description', task, state),
      tools: ['Read', 'Glob', 'Grep'],
    });

    // PHASE 8: Create PR
    await gitPush(worktree);
    const prUrl = await createGitHubPR(task, prBody);

    return prUrl;
  }

  // Run 10 tasks in parallel
  async function main(tasks: Task[]) {
    const results = await Promise.allSettled(
      tasks.map(task => runTask(task))
    );
    // Report results
  }

  Approach?

  Yes. This is the right approach. Here's why, and how to make it 10-year 
  scalable.

  Why it works

  Real engineering teams don't use the same process for a 1-file bug fix and a
  30-file feature. Your separation mirrors how good teams actually operate:

  ┌─────────────┬─────────────────────┬─────────────────────────────────────┐
  │  Task Type  │       Process       │            Why Different            │
  ├─────────────┼─────────────────────┼─────────────────────────────────────┤
  │             │ Investigate → Plan  │ Root cause analysis is the critical │
  │ Bug fix     │ fix → Implement fix │  step. No planning needed beyond    │
  │             │                     │ the fix.                            │
  ├─────────────┼─────────────────────┼─────────────────────────────────────┤
  │             │                     │ Small scope. Planning overhead      │
  │ Enhancement │ Clarify → Implement │ would slow things down without      │
  │             │                     │ adding value.                       │
  ├─────────────┼─────────────────────┼─────────────────────────────────────┤
  │ Feature     │ Clarify → Plan →    │ Large scope. Planning prevents      │
  │             │ Implement           │ costly mid-implementation pivots.   │
  └─────────────┴─────────────────────┴─────────────────────────────────────┘

  This is correct and should not change.

  How to Make It Scalable for 10 Years

  The key insight: separate what changes from what stays stable.

  stacks/ui/react/agents/

  │   ├── enhancement.yaml               ← Defines: clarity → implement → test →

  Scalability Principles

  1. Agents are composable, not monolithic. Notice how implement.md,
  pr-review.md, and test-executor.md are shared across workflows. You don't have
   3 different implement agents — you have 1 that's parameterized.
  2. Workflows are declarative. A feature.yaml file just defines the sequence:
  [clarity, feature-plan, implement, test-executor, pr-review, 
  blocker-resolver(loop), pr-description]. Adding a new workflow = defining a
  new sequence from existing agents.
  3. New agents don't break existing workflows. Want to add a "security scan"
  agent? Create security-scan.md, add it to whichever workflows need it. Nothing
   existing changes.
  4. Rules are separated from agents. react-conventions.md is per-project. The
  agents are universal. You can swap React conventions for Vue conventions and
  the same agents work (with a different stack folder).
  5. _shared is the foundation. Anti-hallucination rules, autonomous protocol,
  quality standards — these apply to every agent in every workflow in every
  stack. Change once, applies everywhere.

  The structure supports this naturally:

  ├── ... (hundreds more)

  composed into any workflow. No coupling between agents. No God-object

  only place that knows which agents run in which order.
